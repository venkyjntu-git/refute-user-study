# Refute-Problem Difficulty Study — Web App

FastAPI backend + React frontend implementing the 4-step study flow:

1. **Task description + 3 I/O pairs** — student writes `funcname(args)` /
   expected-output pairs; checked live against the correct code. Each pair is
   marked correct/incorrect, but **the correct code's output is never shown** —
   log attempts for analysis. After a wrong attempt, if the task has
   `io_example_inputs` configured, the student can request two worked
   examples (real `(call, correct-output)` pairs — a deliberate, one-time
   oracle) via `POST /api/step1/examples`; once revealed, resubmitting either
   revealed call as one of the student's own pairs is rejected (`400`),
   enforced both client-side and authoritatively server-side via the same
   `sandbox.canonical_call` comparison the pairwise-duplicate check uses.
2. **Trace buggy code** — shown once all 3 pairs are correct, as up to two
   separate questions over *different* sample inputs:
   - **Control flow** (`trace_sample_inputs`) — a table listing **every
     line of the function** (not just the ones that run): say **how many
     times** each line executes (0 if never — subsumes plain yes/no for
     non-looping code, extends to loop bodies that run more than once). No
     variable values are asked here at all — that's the data-flow
     question's job, kept deliberately separate so a wrong answer always
     means a control-flow misread, never an arithmetic slip on a line the
     student traced correctly. Listing every line regardless of outcome is
     itself deliberate too: an earlier one-row-per-executed-line design
     leaked control flow for free (row N+1 always told you the answer to
     row N's "what's next").
   - **Data flow** (`trace_data_flow_inputs`, optional) — a second,
     separate question with its *own* sample input(s): the true execution
     skeleton (line, order) is given outright, and the student only fills
     in variable values. Safe to reveal outright because it's never the
     same call as a control-flow input — see `trace_table.py`'s module
     docstring.

   Both end with a return-value box. Rows and answer keys are generated by
   running the buggy code under `sys.settrace`; the key never reaches the
   browser. **One attempt, no feedback** — scored server-side for analysis
   only. If the task has `mutation_line_number`/`mutation_new_line_text`/
   `mutation_prompt` configured, a third, optional panel shows a specific
   line of the buggy code hypothetically changed to different text, with a
   free-text comprehension prompt about it (e.g. "describe how the
   behavior changes"). Collect-only like the rest of Step 2 — no ground
   truth to grade free text against, so it's never scored and never gates
   submission server-side (only the frontend requires it non-empty before
   allowing submit, matching how count/value cells are already
   client-side-only enforced).
3. **Counter-example** — task description and buggy code shown again, plus
   a recap of the student's **own** Steps 1 and 2 answers (`POST
   /api/step3/my_work` — their I/O pairs, their control-flow counts, their
   data-flow values, their mutation-question response, if any; every field
   is individually allowlisted off the much richer stored payloads, so
   nothing correctness-related from Step 2's zero-feedback design can leak
   through here). Student picks one input (fixed `funcname(` / `)`,
   arguments only, same pattern as Step 1) and **predicts both outputs** —
   what the correct code returns and what the buggy code returns. Backend
   runs the call against both implementations and reports the match/mismatch
   verdict plus RIGHT/WRONG per prediction — **never the real values
   themselves**: Step 3 allows unlimited resubmission, so revealing them
   every attempt would turn it into an oracle for reverse-engineering the
   bug instead of a test of reasoning about it. The session only completes
   when all three are right (valid input + both predictions) —
   `fully_successful` in the response; a valid input with a wrong prediction
   is reported separately and doesn't end the step.
4. **Timing** — every step logs a `shown` and `submitted` server timestamp
   per attempt, so per-step and per-attempt durations are computed from the
   data, not guessed client-side.

The home page (`TaskIntro.jsx`) asks for **institute** (fixed dropdown),
**student ID** (free text), and **language** (Python / C / OCaml), then loads
the first task (lowest `id`) whose `Task.language` matches the selection —
there's no task-id picker for the *first* task; `POST /api/session` resolves
it server-side from `language` alone when `task_id` is omitted. Only Python
tasks are actually runnable today (see "Execution sandboxing" below);
C/OCaml exist as selectable languages in the UI and in `Task.language` so
tasks can be authored for them ahead of each language's execution engine
landing — picking one with no seeded tasks returns a 404 ("no tasks
available yet for language '…'") rather than silently failing.

After a student completes Step 3 for one task (`fully_successful`), the app
automatically continues to the next task for the same language: `App.jsx`
fetches the full ordered (`id`-ascending) task list for the language once,
right after the first session starts, and on "Next problem" calls
`POST /api/session` again with an explicit `task_id` for the next task in
that list, reusing the same `student_identifier`/`institute` (echoed back in
`StartSessionResponse`) so every task's session shares one student identity.
Each task is still its own `StudySession` row — no schema change was needed,
sequencing is purely a frontend loop over `/api/session` calls. When the
list is exhausted, the student sees an "All done" screen instead of another
task.

## Quick start

### Backend
```bash
cd backend
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
python seed_data.py          # inserts the sample tasks (max_of_three plus three
                              # Code-Comprehension-proxy examples — smallest,
                              # count_positives, first_positive)
uvicorn main:app --reload --port 8000
```
API docs: http://localhost:8000/docs

### Frontend
```bash
cd frontend
pnpm install
pnpm start
```
Runs on http://localhost:3000 and proxies `/api/*` to `localhost:8000`
(see `"proxy"` in `package.json`; set `REACT_APP_API_BASE` instead if you
deploy them separately).

## Data model / timing

`StepEvent` rows (`backend/models.py`) are the whole timing story:

| step             | event_type | when it's written                                   |
|------------------|-----------|-------------------------------------------------------|
| task_description | shown     | session start                                          |
| io_pairs         | shown     | session start (shown alongside the description); also once more, with `payload.io_examples_revealed=true`, the first time the student requests the two worked examples |
| io_pairs         | submitted | every Step-1 submission (`attempt_number` increments)  |
| buggy_trace      | shown     | first time Step 1 is fully correct                      |
| buggy_trace      | submitted | the single Step-2 submission                            |
| counter_example  | shown     | first time Step 2 is submitted                           |
| counter_example  | submitted | every Step-3 submission                                  |

Time-on-step = `submitted.timestamp - most_recent_shown.timestamp` for that
`(session_id, step)` pair — compute this in your analysis script rather than
storing a duplicate duration column, so re-shows (e.g. a page refresh) don't
corrupt the record.

Export everything as CSV for stats:
```
GET /api/admin/export.csv
```
Step-2 traces need cell-level rows rather than a JSON blob, so they have
their own exports — one per question type, since the shapes genuinely
differ. Control flow — one row per (session, sample input, source line):
each line's claimed-vs-true count, nothing else, with `first_wrong_line`,
`correct_at_buggy_line`, `final_output_correct` and
`right_answer_wrong_trace` repeated on each row for easy grouping:
```
GET /api/admin/trace_export.csv
```
Data flow — one row per (session, sample input, true execution step, cell);
no count/iteration concept, since the execution order is given, not asked:
```
GET /api/admin/data_flow_export.csv
```
or pull one session's full event log as JSON:
```
GET /api/admin/sessions/{session_id}/events
```

## Adding tasks for the study

Add rows to the `tasks` table (or extend `seed_data.py`) with:
- `language` — `"python"`, `"c"`, or `"ocaml"`; drives the home page's
  language dropdown (`GET /api/languages` lists languages with at least one
  task) and which task `POST /api/session` picks. Only `"python"` has a
  working sandbox right now (see "Execution sandboxing" and "Extending for
  other languages" below) — a C/OCaml task can be authored and selected, but
  submitting Step 1 will fail until that language's execution engine exists.
- `description` — shown verbatim in Step 1
- `function_signature` — display-only header shown above the I/O pair form
- `correct_code` / `buggy_code` — full single-function Python source
- `trace_sample_inputs` — JSON list of the calls you want traced for the
  control-flow question (how many times does each line run — no variable
  values are asked here). Loops are supported: the total steps captured
  across every line and iteration combined is capped at
  `sandbox.MAX_TRACE_STEPS`, so a task with a very long loop gets a
  `truncated` capture (a line whose first occurrence falls after the cutoff
  would misreport as never-reached — a reason to keep loop-heavy calls
  small). Recursion is not supported at all (see "Known simplifications").
  Whether a sample input should expose the bug is a study-design choice —
  the seeded task follows `Method.md` and uses one that doesn't, so Step 2
  measures tracing rather than priming the student for Step 3.
- `trace_data_flow_inputs` — optional JSON list of calls for the **data-flow**
  question: the true execution skeleton is given outright (see above), so
  these calls **must not** also appear in `trace_sample_inputs` — reusing
  one there reveals its execution path, defeating the control-flow question
  for that call. (`main.py`'s `_attach_trace_step` logs a server-side
  warning, not an error, if this happens — a misconfigured task shouldn't
  break Step 1 for a student.) Leave empty/unset for a control-flow-only
  task — this field is purely additive and every existing task keeps
  working unchanged without it.
- `buggy_line_numbers` — optional JSON list, e.g. `[5]`, marking which lines of
  `buggy_code` carry the bug. Analysis-only: enables `correct_at_buggy_line`,
  the metric that separates "misread the code" from "read it fine but couldn't
  build a counter-example". Never shown to students.
- `trace_prefill_steps` — shared by both question types (default 1). For the
  control-flow table: how many leading rows, in *source* order (not
  execution order — the table's literal first row is always the one given),
  arrive with their true count already given. For the data-flow table: how
  many leading rows, in *execution* order this time (the skeleton is already
  execution-ordered), arrive with their values already filled in.
- `trace_omit_unchanged_vars` — default false. Applies only to the
  data-flow table's variable columns (control-flow has none). When true,
  columns whose value never changes across a trace (typically parameters
  that are never reassigned) are dropped. Those cells are readable straight
  off the call and carry no tracing signal, but asking for everything is a
  uniform rule that leaks nothing, hence the conservative default.
- `io_example_inputs` — optional JSON list of calls for Step 1's
  post-wrong-attempt example reveal. Only the first 2 are ever used, run
  against `correct_code` (never `buggy_code` — Step 1 is pure spec
  comprehension). Leave empty/unset to not offer this at all.
- `mutation_line_number` / `mutation_new_line_text` / `mutation_prompt` —
  all three optional together, for Step 2's mutation-question panel: which
  line of `buggy_code` to show hypothetically changed, the replacement
  text, and the free-text comprehension prompt to ask about it. Leave all
  three unset for a task with no mutation question.

After changing any of these on an existing DB, re-run `python seed_data.py`
(it refreshes the trace config on an already-seeded task) — and if you are
upgrading a database whose `tasks` table was created before the relevant
columns existed, run the matching migration script first: `python
migrate_trace.py` (step-2 trace columns), `python
migrate_language_institute.py` (`language`/`institute`), or `python
migrate_step_extras.py` (`io_example_inputs`, the three `mutation_*`
columns, and `study_sessions.io_examples_shown`). All three migration
scripts work on both SQLite and Postgres, are idempotent, and are a no-op
when the table does not exist yet (`create_all` builds it with the columns
already in place).

## Execution sandboxing — read before running this on students' machines/servers

`backend/sandbox.py` runs each function call in a **separate Python
subprocess** (`python -I`, isolated mode) with a wall-clock timeout and
best-effort CPU/memory `rlimit`s on POSIX. This stops accidental infinite
loops or runaway memory use and prevents student input from touching the
FastAPI process's own namespace. It is **not** a hardened multi-tenant
sandbox: there's no container/VM boundary, no seccomp filter, and no
network/filesystem jail, so a student who deliberately wrote malicious code
(rather than a CS1 bug) could still do things a subprocess can do (e.g. read
files the server process can read).

For a supervised, IRB-style user study where the "attacker" is a CS1 student
typing ordinary buggy expressions, this is a reasonable trade-off. If you're
deploying this as an open, unsupervised, public-facing tool, swap
`sandbox.run_call` for a real isolated execution service (Docker container
with `--network none` + strict cgroup limits, gVisor/Firecracker, or a
hosted code-execution API like Judge0/Piston) — the function signature
(`run_call(code, call) -> ExecResult`) is designed so that's a drop-in swap.

On top of the process isolation, `sandbox._check_call_syntax` restricts every
submitted "call" string to a single call of a function actually defined in
the task's code, with every argument required to be an `ast.literal_eval`-able
literal — so a student can't smuggle in an arbitrary expression (e.g.
`__import__("os").system(...)`) as the "call." The frontend also fixes the
function name and parentheses as non-editable decoration around the
arguments field, so a student never even types the callee. Neither of these
is a substitute for the subprocess isolation above — they close a specific
injection path, not the general one.

## Extending for other languages (e.g. C, OCaml)

The pipeline (I/O pairs → buggy trace → counter-example, each timestamped),
`Task.language`, and the home-page language picker already exist — what's
missing per language is the execution engine itself. To support C:
- Replace `sandbox.run_call` with a compile-then-run step (`gcc`, temp
  binary, subprocess with the same rlimits/timeout).
- `values_equal` will need a C-output-aware comparison (stdout string
  compare is simplest if the student's function prints instead of returns).
- Step 2's trace capture (`sandbox.capture_trace`) is the hard part: there's
  no C equivalent of `sys.settrace`. Realistic options are scripting GDB
  (`-batch -x`, or its MI protocol) to single-step and dump locals per line
  compiled at `-O0`, or source-to-source instrumentation with a real C parser
  (e.g. tree-sitter-c) that injects a "dump locals" call after every
  statement. Budget real time for this regardless of which approach you pick.

OCaml is harder still, and not only technically: idiomatic OCaml for a CS1
task tends to be a handful of `let`-bindings and pattern matches (each value
bound once, often recursive) rather than a sequence of lines that mutate
variable state — the trace table's core device ("the value of every variable
**after** this line") doesn't map cleanly onto that. Treat the Step-2 design
for OCaml as an open question, not just a porting task, before building a
tracer for it.

## Known simplifications worth deciding on before running the real study

- **Retries**: Step 1 allows unlimited resubmission attempts (all logged via
  `attempt_number`) until all 3 pairs are correct. If you want to cap
  attempts or study give-up behavior, gate `/api/step1/submit` on attempt
  count and add a "skip" event type. Step 2 is capped at exactly one attempt
  by design (a second POST returns 400): with no feedback there is nothing to
  learn from resubmitting, and allowing one would muddy the step-2 timing.
- **Blank trace cells**: the control-flow UI requires a valid count for
  every line before it will submit (there's nothing else to fill in there).
  The data-flow table's variable-value cells are optional — a student can
  leave one blank (e.g. if unsure a variable is in scope yet) and it's
  simply not scored, rather than treated as "I don't know" versus a guess.
  If you want that distinction captured explicitly, add a `?` option to the
  value cells — decide before the real run.
- **Recursive tasks**: the trace table is one row per *physical source
  line*, with the student asked how many times it runs (loops are handled
  this way). A recursive call doesn't fit the same shape — a line inside a
  recursive call needs one row per call depth, and potentially a different
  code path per depth, not a flat per-line count. Fine for the non-recursive
  CS1 tasks this was built for; revisit the design (not just the code) before
  using a recursive task.
- **Float outputs**: `values_equal`/counter-example comparison uses exact
  `repr()` equality. If any task involves floats, add a tolerance-based
  comparison instead of strict inequality/equality.
- **Auth**: `student_identifier` is a free-text field, not authenticated.
  Fine for a lab study with an issued ID; add real auth if deploying broadly.
- **Institute**: chosen from a fixed dropdown in the UI for consistency, but
  `StudySession.institute` is a plain string, not validated or constrained
  server-side (same trust level as `student_identifier` — study metadata,
  not access control).
- **C/OCaml are selectable but not runnable**: the home page offers all three
  languages and `Task.language` supports seeding non-Python tasks, but
  `sandbox.py` only executes Python. Selecting C/OCaml with no seeded task
  for that language 404s at session start; seeding one without an execution
  engine gets you into Step 1 only to have every submission fail. Decide
  which of these two states you want before pointing real students at a
  non-Python language — see "Extending for other languages" above.
- **Step 1 example reveal is a deliberate, one-time oracle**: unlike
  everywhere else in the app, `POST /api/step1/examples` does return the
  real correct-code output for two author-chosen calls. It's gated on
  having already gotten a submission wrong, but nothing stops a student
  from requesting it and never submitting their own three pairs honestly
  first — that's an accepted trade-off (a scaffold, not a second gate), not
  an oversight.
- **Mutation-question responses are never graded**: `mutation_response` is
  free text with no auto-gradable ground truth, stored for qualitative
  analysis only, and (unlike every count/value cell in Step 2) the frontend
  is the *only* place that requires it non-empty — the server accepts a
  missing/empty response without complaint, same as it already tolerates
  missing trace cells. If you want a hard server-side requirement, add one
  in `submit_trace`; today it deliberately doesn't have one.
- **Task order is fixed (`id` ascending), not randomized or
  counterbalanced**: `seed_data.py` inserts four Python tasks
  (`max_of_three`, `smallest`, `count_positives`, `first_positive`), and
  every student who picks Python now works through all four, in that same
  fixed order — `App.jsx` fetches `GET /api/tasks`, filters/sorts by `id`
  for the chosen language, and steps through it via `POST /api/session`
  with an explicit `task_id` after each `fully_successful` Step 3. There's
  no per-participant shuffling or A/B task-order assignment; if the study
  design needs counterbalancing to rule out order effects, that logic
  still needs to be added (e.g. seeding a random or Latin-square order per
  `student_identifier`/`institute` rather than always sorting by `id`).
